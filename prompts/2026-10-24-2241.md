### Response

**GREEN: `create-admin` command.** The full suite now passes (27 tests) and ruff is clean. Nothing is committed.

**Service** (`app/services/auth.py`): `create_admin(email, password)` looks the email up first and returns that user if it already exists. Otherwise it saves a new user with a hashed password and role `admin`. Both seeding tests went from failing to passing.

**Command** (`app/cli.py`):

```bash
uv run python -m app.cli create-admin
```

- `ADMIN_EMAIL` and `ADMIN_PASSWORD` are optional fields on `Settings`, so they come from the environment or `.env` like the rest of the config. Example values are in `.env.example`.
- The command creates the tables if they don't exist yet, so it works on a fresh database.
- If either variable is missing, it prints an error and exits with code 1.

Run by hand against a throwaway database:
- Running it twice printed `Admin ready: root@example.com` both times and left one row, `('root@example.com', 'admin')`.
- With `ADMIN_PASSWORD` unset it exited with code 1.

Things to know before committing:
- **The command has no automated test.** The brief asked for it in GREEN, but the working agreement says no production code without a failing test. Only the service is covered by tests.
- **An existing regular user is not promoted.** If the email already belongs to a regular user, `create_admin` returns that user unchanged and the command still prints "Admin ready".
- **The email is stored as given.** `register` lowercases emails, but `create_admin` doesn't.

Each of these could be its own RED cycle.
