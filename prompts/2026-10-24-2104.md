Elaborate on the choices to revisit. Explain the options, the merits, and demerits for each option, and your own recommendation. Explain what exactly you would change for each of these.

### Response

My recommendations in short: keep the engine on the app, make the JWT secret required, and add CORS in its own test-first cycle.

#### 1. Where the engine and session factory live

Right now `create_app(settings)` builds its own engine and stores the session factory on `app.state`. `get_session(request)` gets its sessions from there. Separately, conftest creates a second engine on the same temporary file and overrides `get_session` with it.

| Option | Merits | Demerits |
|---|---|---|
| **A. Engine per app on `app.state` (current)** | `create_app(settings)` really does control the database. Importing the app doesn't open a connection. Two apps (say, two tests) can't share state by accident. | Less common than the FastAPI tutorial style. `get_session` needs `Request`. The test override is mostly redundant. Each test opens two engines on one file. |
| **B. One engine for the whole module, built from `get_settings()` when the module loads** (the tutorial pattern) | Familiar and very little code. Overriding `get_session` is the only way tests swap the database, so that part is clear. | `create_app(settings)` would ignore the `DATABASE_URL` you pass it, which makes the signature misleading. The engine points at `dev.db` as soon as you import the module, tests included. The lifespan's table creation would run on the dev engine, not the test one, unless you patch around it. That's exactly the "tests must never touch the dev DB" risk. |
| **C. A cached `get_engine(url)` function** | Builds lazily and allows one engine per URL. | It's still a global cache that can leak between tests, and it's more moving parts than A without a real gain. |

**My recommendation: keep A, with two small changes:**
- **Store the engine:** in `app/main.py`, set `app.state.engine = engine` next to the session factory. Later code, and tests that need to inspect the schema, can then reach it without building a new one.
- **Build the override from the app's own factory:** in `tests/conftest.py`, drop the separate engine and have the `session_factory` fixture return `app.state.session_factory`. The override stays. Its real value later is per-test rollback: open a connection, begin a transaction, bind the session to it, and roll back at the end.

#### 2. The `JWT_SECRET` default

Right now it falls back to `"dev-secret-change-me"`. The reason is that `app/main.py` runs `app = create_app()` as soon as it's imported, and conftest imports `app.main`. A required secret would make test collection fail whenever the env var is missing.

There's a second problem: the `"test-secret"` value in conftest is 11 bytes. Recent PyJWT versions warn when an HMAC key is shorter than the hash output, which is 32 bytes for HS256. It will start warning as soon as we sign tokens.

| Option | Merits | Demerits |
|---|---|---|
| **A. Keep a dev default (current)** | Works with no setup and the fresh-clone check passes trivially. | A deploy with a missing env var still starts and signs tokens with a public, known secret. Nothing stops it. |
| **B. Required, no default** | Fails loudly at startup if it isn't set, which is the safe choice for an auth app. | Something else has to supply it: a `.env` for dev, and tests need a way around the import-time `create_app()`. |
| **C. Default allowed, with a guard** (e.g. reject the default when `APP_ENV=production`) | Dev stays convenient and production is protected. | It's a new setting to remember, and the protection only holds if `APP_ENV` is set correctly. That's the same kind of mistake it's meant to catch. |
| **D. Required and wrapped in `SecretStr`** | Also keeps the secret out of reprs and logs. | Every use needs `.get_secret_value()`, which is a bit more ceremony. |

**My recommendation: B, plus a minimum length:**
- **Settings:** in `app/core/config.py`, change the field to `JWT_SECRET: str = Field(min_length=32)`.
- **Move the factory:** move `create_app` into a new module, `app/factory.py`. Then `app/main.py` contains only `from app.factory import create_app` and `app = create_app()`. Conftest imports from `app.factory`, so it never touches `main.py`'s import-time app, and tests always pass explicit settings. This is cleaner than setting `os.environ` at the top of conftest before imports, which needs `# noqa: E402`, or adding the pytest-env plugin.
- **Test secret:** in conftest, use a secret of at least 32 characters, e.g. `"test-secret-" + "x" * 32`.
- **`.env.example`:** add one at `backend/.env.example` with `DATABASE_URL`, a placeholder `JWT_SECRET`, `JWT_EXPIRE_MINUTES` and `CORS_ORIGINS`. It's already on the dev plan, and `.gitignore` already allows it. Developers copy it to `.env`, which pydantic-settings already reads.

I'd skip `SecretStr` for now. It's a reasonable extra later, but it isn't needed for safety once the secret is required.

#### 3. `CORS_ORIGINS` exists but isn't connected

The dev plan uses JWT **bearer** tokens and may deploy to Vercel. That means the browser sends an `Authorization` header and doesn't need cookies, so CORS only has to allow that header and doesn't need `allow_credentials`. A frontend on Vercel would be a different origin from the API, so production will need CORS eventually.

| Option | Merits | Demerits |
|---|---|---|
| **A. Leave it unused for now (current)** | Follows the "no production code without a failing test" rule exactly. | An unused setting is a bit misleading, and the frontend's first call will fail with a CORS error. |
| **B. Add `CORSMiddleware` now, without a test** | One line, done. | Breaks the TDD agreement, and a wrong origin or header list only shows up in the browser. |
| **C. Add it with a test, as its own red/green cycle** | It's tested. It also shows that settings flow from `create_app(settings)` to behaviour. | One more cycle, though a small one. |
| **D. Avoid CORS in dev with a Vite proxy** (`server.proxy: { "/api": "http://localhost:8000" }`) | The frontend calls the same origin in dev, so there's no CORS config to get wrong locally. | It doesn't solve production on Vercel. You'd still need C, or a Vercel rewrite that proxies `/api`, later. |

**My recommendation: C, as the next TDD cycle, and optionally D for local development.**
- **RED:** add `tests/test_cors.py`. It builds settings with `CORS_ORIGINS=["http://allowed.test"]` and sends a preflight `OPTIONS /api/health` with `Origin: http://allowed.test` and `Access-Control-Request-Method: GET`. It asserts that `access-control-allow-origin` equals that origin. A second test checks that a different origin doesn't get the header.
- **GREEN:** in `create_app`, add `app.add_middleware(CORSMiddleware, allow_origins=settings.CORS_ORIGINS, allow_methods=["*"], allow_headers=["Authorization", "Content-Type"])`.
- **Env-var format:** by default, pydantic-settings reads a `list[str]` from the environment as **JSON**, e.g. `CORS_ORIGINS='["http://localhost:5173"]'`. For a comma-separated value in `.env`, mark the field with `Annotated[list[str], NoDecode]` and add a `field_validator(mode="before")` that splits on commas. JSON is fine if documented in `.env.example`.
